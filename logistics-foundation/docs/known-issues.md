# Known Limitations and Risks (v0.4.2)

This file honestly records items still unmet or met only conditionally; "not reproduced" must not be written as "no risk".

1. **Local demo only, not a production system.** No TLS termination, reverse proxy, backups, monitoring, or public-network hardening; HTTPS-related behavior (Cookie `Secure`) exists only on the code path and has not been verified with a real certificate deployment.
2. **Dependency risks not zeroed (measured 2026-11-01).** `npm audit --json` shows **3 high + 16 moderate**, and `npm audit --omit=dev --json` still shows **3 high**. The raw outputs are `evidence/audit.json` and `evidence/audit-omit-dev.json` in the delivery package; commands/exit codes/summaries are in `evidence/audit-summary.json` and `test-logs/`. The high chain is `prisma → @prisma/config → deepmerge-ts` (GHSA-ggr8-5vv4-36mx, recursive object-graph merging can exhaust the call stack); the three package counts come from the same dependency chain and must not be read as three independent root vulnerabilities. `prisma` is in current dependencies, so omit=dev does not exclude this chain; the blanket claim "dev-only/non-runtime, so the runtime is risk-free" is retracted. It is currently unproven whether the business HTTP path is exploitable, and also unproven that it is not. The 16 moderate are package-level counts of ESLint-related packages and the minimatch chain; the raw advisory is GHSA-g3hv-75wg-m249 (globparts amplification, potential denial of service); that moderate chain does not appear in this round's omit=dev output, which does not mean all dependency risks are gone. Scan suggestions involve cross-major-version changes such as Prisma 7, and some would even change the current ESLint/Next version combination; this round keeps locked dependencies, does not run `npm audit fix --force`, does not blindly override, and does not falsely claim fixes.
3. **SQLite single writer.** Concurrent write conflicts retry within bounds and may finally return 503; enterprise-grade throughput is not promised. Race tests cover "duplicate confirm/cancel/ship on the same order, two orders competing for the same stock, cancel-vs-pick races", but no high-concurrency load testing was done.
4. **Login rate limiting is an in-process counter.** Multiple processes or a restart reset it; demo-grade, not a credential-stuffing defense. Limits are counted per normalized email and client proxy headers are ignored; rotating X-Forwarded-For still hits the same account limit. No cross-process rate limiting or separate global request throttling is implemented.
5. **Session management.** Fixed 8-hour expiry with no sliding renewal; changing a password/deleting a user does not actively kick existing sessions (password change is not implemented in this project). The session table has no periodic cleanup job; expired rows are deleted when that token is next accessed.
6. **CSRF uses a server-side token + Origin check**; double-submit cookies are not implemented, and cross-site embedding scenarios are untested.
7. **Amounts and payments.** Only integer cents and an order-placement snapshot exist; there is no payment, refund, or reconciliation; "delivered order amount / non-cancelled order amount" is not a revenue measure.
8. **Logistics is simulated.** The carrier is 1–40 characters of free text; pickup/delivery are triggered manually by staff and do not represent real carrier callbacks or GPS.
9. **Report measures.** Orders are attributed to GMT+8 calendar days by `createdAt`; inventory metrics are a current snapshot, not filtered by date; CSV exports only the order dimension without item details.
10. **Numbering.** Order `ORD-YYYYMMDD-XXXX` and shipment `LG-YYYYMMDD-XXXXXX` numbers use UTC calendar days while the UI displays GMT+8, so numbers cross dates at night; daily caps are 9999 / 999999 respectively, and exhaustion returns a readable 503.
11. **Create idempotency.** The frontend prevents double clicks and, when the network result is unknown, guides the user to check "My Orders", but there is no server-side idempotency key; extreme repeated submissions can still create two orders.
12. **Seed is destructive.** It requires an explicit `RESET_DEMO_DATA=YES` and is only for brand-new/disposable databases; it never wipes the database on default startup. The evidence entry point likewise requires explicit caller confirmation and initializes a new database only in a separate temporary source copy; the original project database is not involved.
13. **Demo password.** The default `Demo1234!` is for local demo only and can be overridden with `DEMO_PASSWORD`; the delivery package contains no real secrets.
14. **Test scope.** Browser acceptance was completed on Chromium alone; no Safari/Firefox, no real screen readers, no WCAG certification, and no long-term availability (08:00–24:00) testing. Accessibility covers only basic checks such as visible labels, keyboard focus, and non-color-only distinctions.
15. **Prisma CLI environment-variable gotcha.** If the shell sets `RUST_LOG`, Prisma reports an empty `Schema engine error` when the database file does not yet exist (its stderr parsing assumes the first line is a banner). Run `unset RUST_LOG` before Prisma commands locally, or `touch prisma/dev.db` first; CI is unaffected.
16. **Not implemented (explicitly out of scope this round).** Public registration, password recovery, OAuth/MFA, user management, real payments/refunds, real carrier APIs, email/SMS/push, multi-warehouse multi-tenancy, procurement, returns, native mobile apps, Docker/public hosting, any new course documentation.
